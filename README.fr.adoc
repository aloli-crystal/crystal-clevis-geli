====
Ce shard est *en cours de dépréciation au profit de
`crystal-clevis-zfs`*.

*Pourquoi ce changement ?* — analyse comparative GELI vs ZFS
native encryption pour le cas d'usage Aloli (FreeBSD + ZFS) :

* *Performance* : ZFS native encryption gagne largement quand les
  données sont compressibles (logs, BDD, JSON, code), parce que la
  compression ZFS s'applique *avant* le chiffrement. Avec GELI, ZFS
  voit du bruit cryptographique et la compression devient inutile.
* *Simplicité du boot* : un seul pool ZFS, datasets chiffrés
  enfants, deux commandes (`zpool import` + `zfs load-key`) au
  lieu d'une chaîne `geli attach × N` + `zpool import × N`.
* *Snapshots / send-recv* : ZFS native permet `zfs send -w` qui
  exporte les snapshots chiffrés tels quels — backups off-site
  sans clé devient possible.

`clevis-geli` v0.1 reste *fonctionnel et testé* (banc QEMU
FreeBSD 15 aarch64). Le code n'est pas archivé tant que
`crystal-clevis-zfs` n'est pas livré et fonctionnel — vous pouvez
continuer à l'utiliser pendant la transition.

*Migration prévue* : les utilisateurs Aloli passent à
`crystal-clevis-zfs` au prochain re-bootstrap de chaque serveur.
Pas de migration in-place forcée.

*Référence* : voir le document
https://github.com/aloli-crystal/beryl/blob/production/crystal-clevis-zfs-specs.adoc[crystal-clevis-zfs-specs.adoc]
côté `beryl` pour les spécifications du successeur, et
https://github.com/aloli-crystal/beryl/blob/production/boot-and-mount-plan.adoc[boot-and-mount-plan.adoc]
§ « Pivot GELI → ZFS native » pour la justification détaillée.

*Pour la communauté FreeBSD* : si quelqu'un a un usage Tang+GELI
(Tang+UFS, Tang+ext4 portable, etc.) qui ne se traduit pas en
Tang+ZFS, ce shard reste utilisable et open source. Les forks
sont les bienvenus.
====

Équivalent FreeBSD/GELI de https://github.com/latchset/clevis[latchset/clevis].

`clevis-geli` implémente le protocole client Tang
(Network-Bound Disk Encryption — NBDE) pour permettre aux volumes
GELI chiffrés d'être déverrouillés **au boot, sans intervention
humaine**, en interrogeant un ou plusieurs serveurs Tang.

Cette brique n'existe nulle part dans l'écosystème FreeBSD
aujourd'hui. C'est le manque que ce shard comble.

Version anglaise : link:README.adoc[README.adoc].

== Architecture

[source]
----
                  ┌────────────────────────────────┐
                  │    clevis-geli (this)  │
                  │                                │
                  │  bind / recover  ── geli setkey│
                  │  Tang HTTP/JOSE                │
                  └─────────────┬──────────────────┘
                                │
                                │ HTTP + JOSE
                                ▼
                       ┌────────────────┐
                       │ Serveur(s) Tang│
                       │ (pkg FreeBSD)  │
                       └────────────────┘
----

== Utilisation (prévue)

[source,shell]
----
# Lier un volume GELI à deux serveurs Tang (threshold 2 sur 2) :
clevis-geli bind \
    --device /dev/ada0p4 \
    --tang http://tang-nas.local \
    --tang http://tang-ovh.example.com

# Déverrouiller un volume lié au boot (depuis rc.d) :
clevis-geli unlock --device /dev/ada0p4
----

== État

* **v0.1** : protocole client Tang (advertise, recover) sur
  `jose`. Primitives JOSE validées contre `latchset/jose`.
* **v0.1** : binding GELI via shell-out `geli(8)`.
* **v0.2 (plus tard)** : threshold Shamir sur plusieurs serveurs
  Tang (`sss` à la Clevis).
